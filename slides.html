What this thing actually is

Gather context
→
Take action
→
Verify results

It reads your files, runs commands and edits code in a loop. The phases blend: a question may only need the first, a bug fix cycles all three. And you are inside the loop, not waiting outside it - you can interrupt and steer at any point.

The third phase is the one people skip, and every tool we build later exists to protect it. Note also: almost none of this is really about Claude Code. The same moves work in any CLI coding agent.

Where to look - what done means - what to reuse - what not to do - how we will know. Write those five and you have written a good prompt. Miss the last one and you have written a wish.

Foundations

Two properties you cannot prompt away

Not
deterministic
Same prompt, same repo, genuinely different runs. There is no seed to find. You already know why. What matters is the consequence: you cannot rely on having got a good result once.
It
forgets
Every session starts with a fresh context window. Yesterday's conversation is gone. So it has no private memory of your landmines - it copies whatever is already in the codebase. A human in a messy repo builds up scar tissue and routes around it. An agent starts cold every time.
You don't fix either one by prompting harder. You fix the outcome by making it checkable, and you fix the forgetting by writing things down instead of saying them once.

Foundations

The idea everybody repeats. Worth knowing exactly how firm it is.

SMART ZONEDUMB ZONE
empty sessionfull window

As a session fills up, quality drops before capacity runs out. Finding a fact deep in the window is fine. Reasoning over everything that piled up is the part that goes - and it never stops sounding confident while it happens.

Whose idea this is

Matt Pocock (AI Hero) named the smart zone / dumb zone; Dex Horthy (HumanLayer) argues the same thing as a context-utilization budget. It comes from people who use these tools all day, not from a benchmark. Treat it as a working rule of thumb, because that is what its own authors call it.

Nobody has published the number

The people who do this all day land near 100K. The defaults ship far higher:

80-100K Pocock's smart zone, restated after 1M shipped
~100K Horthy: do the work in the first 100K
100K Anthropic starts clearing tool results
~967K Claude Code's auto-compact default

Your tool will let you run to 967K. Nobody who writes about this works anywhere near it.

You have a meter and a red line. This is what you do about it.

CommandWhat it doesWhen
/clearnew conversation, empty contextswitching to unrelated work
/compactreplaces history with a summarymid-task, need room, not a reset
/compact <focus>same, steeredsay what you're about to do next

That third row: you can type a sentence after /compact telling it what the summary should hold on to. Say what you are about to do next, not what you want kept - /compact I'm moving from building to QA beats guessing which parts of the last hour mattered, because you always know your next task and you rarely know that.

If in doubt, clear

Every compaction is a model summarising your conversation, and each pass leaves sediment - summaries layered on summaries, including work you finished an hour ago. Compact a few times in a row and it is reasoning from compressed leftovers. Compact only when you would genuinely lose something expensive, like a long debugging session where you have ruled things out.

Clearing is not losing

/resume brings the conversation back, scoped to the repo you are standing in - which is where people trip. And a second, less obvious reason to clear: you cannot tell what your own setup did if the agent already knew it from twenty messages ago. Test your own files in a fresh session.

Files on disk survive a reset. Things you only said in chat do not. Which is the entire argument for writing your setup down instead of explaining it again every morning.

Esc Esc on an empty input - the rewind menu

> Restore code only
  Restore conversation only
  Restore code and conversation
  Summarize from here
  Summarize up to here
  Never mind

Esc interrupts mid-turn so you can redirect - work done so far is kept. If a dialog is open it closes the dialog instead.

Esc Esc on an empty input opens this menu. With text in the input it clears your draft instead, and saves it, so Up gets it back.

The first entry is the one nobody expects: bin the bad edits, keep everything it figured out.

What rewind does not cover

  • Bash changes aren't tracked.If it ran rm or mv, rewind will not bring it back.
  • Most subagent edits aren't restored.
  • Symlinked and hard-linked files aren't either.A restore skips them and prints “Restored the code, but skipped N files”. If you use pnpm or a dotfile manager, that's you.
  • It is not version control.Session-level undo. Commit before you let it do anything big and you always have the real floor underneath.

Foundations

Prefix any command with ! and Claude sees the result without you pasting it

> ! pytest -k test_expired_token

FAILED test_expired_token
  AssertionError: expected 401, got 500

Claude reads that output and answers it
on its own - no second prompt from you.

The universal beginner habit is: run the test in a second terminal, read the failure, select it, copy it, alt-tab back, paste it. Thirty seconds of clerical work per loop, so you stop closing the loop.

Why one character is worth a slide

The habit is make the check happen, and put the result in front of the model. This is that with the friction removed - no second terminal, no selecting, no alt-tab. If you take one keystroke away from this session, take this one.

Two warnings

Output in context is context spent. Anthropic's own docs: the window holds every message, every file read and every command output, and performance degrades as it fills. ! on something that prints ten thousand lines of build log spends your window on build log. Narrow the command first.

It actually runs it. This is not a preview. ! on something that flashes a device flashes the device.

Three more, and the first one is worth memorising

@ a path puts that file in context for certain instead of hoping it gets found - but you pay for the whole file, plus the CLAUDE.md from its directory and every parent above it. @ a 3,000-line file and you have spent your window on it.

Ctrl+B runs something alongside, when you do not want to block on it. Long-lived processes. (In tmux, press it twice.)

Ctrl+Z then fg keeps a command private - Claude sees neither the command nor the output. Unix only.

Foundations

Your tests are even more important now

A repo with fast, real tests is a repo where an agent can work and check itself. A repo without them is one where you review every line, forever.

That is the whole reason the test suite stops being hygiene you keep postponing and becomes the thing that decides whether any of this is useful here.

The agent will also be the one writing new tests - and left alone it writes them in five different styles, mocks things it should not, and produces a suite nobody trusts. Which means it cannot trust it either, and you are back to reviewing every line.

So write down how tests get written here. Once.

.claude/rules/testing.md

---
paths:
  - "**/*.test.ts"
  - "tests/**"
---
- One behaviour per test. No test
  asserts two unrelated things.
- Mock the network boundary only.
  Never mock something we own.
- Test names read as sentences:
  "rejects an expired token".
- No snapshot tests for logic.
- A new test must fail before the
  change that makes it pass.
- If a test needs a comment to
  explain it, rewrite the test.

The paths: - they make sure this loads only when Claude touches a test file, so it costs you nothing on every other request.

Your tests are the ceiling on how much you can trust your agent working in your repo - and your rules for writing tests are the ceiling on how long that stays true.

The guardrails - you already own all six

These are how the work gets checked: they tell you and the agent whether it worked, they catch what it broke on the way, and they are the only way it can correct itself without asking you. The split that matters is which ones it can run on its own.

LoopAgent can run it alone?
Typecheck / compileyes, unattended
Testsyes, unattended - if you can run one by name
Lint / static analysisyes, unattended
Code reviewno - a person, or a pipeline you build later
Manual QAno - a person at a screen or a rig
CIno - runs after the fact, not in the loop

Give each one a name it can type

Do not leave these as flags people have to remember. Put every loop behind one short prepared command - a justfile target, an npm script, a make rule, a shell script in the repo - and commit it.

just check      # typecheck
just test auth  # one test by name
just lint

Why that is the whole trick

You and the agent then run the identical command, so “it passes on my machine” stops being a conversation. It is one line in your CLAUDE.md instead of six. And when the command changes you fix it in one place rather than in everybody's habits.

Paste at the end of any non-trivial request

If you are not sure about something do not
assume - interview me relentlessly.

Write the result to docs/notes/<thing>.md

Make it interview you

Left alone it answers from assumptions rather than asking. Forcing it to interrogate you first is what stops it doing the wrong thing extremely well.

Write it to an exact path

An answer in a chat window dies with the session. A named file is a thing your team can read, review and commit. Note exact - “write it to a file” gets you a file somewhere you will not find.

Things genuinely worth having it write down

A research note. Three approaches to a problem you have not solved, the trade-offs, and which one you picked. Pay the research cost once instead of every session.

An ADR. What was decided, what else was considered, why. The one thing an agent can never work out from the code.

A glossary. Your team's private words, one line each. This is also the honest answer to “what do I put in a CLAUDE.md?”

An analysis. A call-graph walk, a memory-layout note, “here is where this state machine can deadlock”. Useless in a scrollback buffer, valuable in a repo.

The plan itself. Phases, in a file you can review in a minute instead of a diff you would review in a day.

A spec, with an Out of Scope section. The part of a spec that actually stops an agent is the list of what it must not build.

Why bother writing markdown for a robot

Agents perform better in well-organised codebases for exactly the same reasons new hires do. The agent is a new hire who starts fresh every twenty minutes. So “how well does Claude do in my repo?” is really “how fast could a competent stranger orient in my repo?” Are related things grouped. Is anything named for what it does. Is there any written statement of how the thing gets built.

CLAUDE.mdalways loaded
.claude/rules/loaded by path
.claude/skills/loaded on demand
hooksrun on an event
settings.jsonpermission policy
None of this is Claude Code magic. It's five kinds of file, and the whole skill is knowing which one a given piece of knowledge belongs in. If your repo isn't well-organised and you can't fix that: this file is where you write down how it's a mess so the agent stops tripping on it.

Your setup

Three rules - and the third is the highest-value line in the file

These apply to anything you write for the agent to read - the always-on CLAUDE.md, a scoped file in .claude/rules/, the body of a skill. Where a thing lives is the next slide; how to write it so it survives contact with the repo is the same in all three.

Rule 1

Patterns, not paths and signatures

Rules describe patterns, not
APIs. The source is the
reference for signatures
and types.

“Auth lives in src/auth/handlers.ts” is true for about a month, then it's a confident wrong turn. Humans skim a stale doc sceptically. Agents do not - it re-reads yours every request. Describe what the code does and let it find the files. Its map is current. Yours is not.

Rule 2

One sentence, then a rejected example

Errors return the existing
ApiError shape.
BAD:  throw new Error("bad email")
GOOD: return apiError(400, "...")

Not a paragraph in capital letters. Shouting at a model doesn't work; showing it something you rejected does. One line of intent, one pair, done.

Rule 3

A required planning step

Before writing code, list the
modules you will add or change
and their public interfaces,
then wait for my confirmation.

One sentence, and it changes the shape of what comes back: you review a five-line sketch instead of a diff. Generalises to anything you want always considered - security, migration safety - as an explicit step with a human checkpoint.

The honest caveat, and you need it: three things steer a session - your prompt, this file, and the code already in the repo. The code is the strongest. If the pattern you banned appears fifty times in the codebase, the ban often loses. Writing the rule down is necessary, not sufficient. Two real fixes, both better than a longer file: point at a good reference file to imitate, or back the rule with a hook.

A shell command the harness runs on an event

Prompts are suggestions.
Hooks are guarantees.

SessionStart

Force-load a rulebook, so the thing you care about is in context before anyone types a word. This one does spend context, by design - SessionStart output goes to Claude.

PostToolUse

Run your formatter after every edit. This is the one that converts “please match our style” from a paragraph in CLAUDE.md into something that simply is true. clang-format -i - ruff check --fix - spotlessApply - Prettier - same trade, different body.

Same rule, two places. Put always run Prettier after editing in CLAUDE.md and it is a sentence the model re-reads every session and follows most of the time - it costs you those tokens in every session forever, and it gets less reliable the longer the session runs. Put it on PostToolUse and the harness runs prettier --write itself: edit 300 behaves exactly like edit 1, it costs zero context until it fires, and it also catches the teammate who never read your CLAUDE.md.

About thirty events exist. These are the ones people actually use.

EventFiresWhat you'd use it for
SessionStartsession begins or resumesforce-load a rulebook before anyone types
UserPromptSubmityou send a prompt, before Claude sees itinject a standing reminder
PreToolUsebefore a tool call runsblock it outright
PostToolUseafter a tool call succeedsrun your formatter
StopClaude finishes respondingrefuse to finish until the check passes
PreCompactbefore context is compactedwrite state to a file first

You do not need to memorise the rest, and you do not need to write the JSON by hand either: ask Claude Code to list the events it supports, or to write the hook for you. It knows its own harness.

.claude/settings.json

{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{
        "type": "command",
        "command": ".claude/hooks/format.sh"
      }]
    }]
  }
}

A matcher and a command. That is the whole thing. The script gets the tool call on stdin as JSON, so it can read which file was just written. (Prefix the path with ${CLAUDE_PROJECT_DIR}/ if it has to work from any directory.)

Exit 0 lets it through. Exit 2 blocks, and whatever the script printed to stderr goes to Claude as the reason. That is the entire contract.

The one thing worth getting right is where a hook can say no. PreToolUse blocks the call before it happens and Stop blocks the turn from ending. PostToolUse cannot block anything - the tool already ran, so it can fix and it can complain, but it can never prevent. If the rule must hold, it goes on the event that fires first.

Setting permissions for your agents

{
  "permissions": {
    "allow": [
      "<your test command>",
      "<your build command>",
      "<your linter>",
      "<read-only git>"
    ],
    "ask":   [ "<warn me, don't block me>" ],
    "deny":  [ "<push>",
               "<force-push>",
               "<anything destructive>" ]
  }
}
  • Allow broadly.Wildcard the safe families so you're not clicking approve all day. Build, test, lint, read-only git.
  • Deny narrowly.Blocks outright - no dialog, no override. This is the answer to “but what if it does something stupid”: write down the handful of things it's never allowed to do, once, and stop worrying.
  • Yours vs the team's.Keep it to yourself and it is your own safety net. Share it with your team and everyone on the repo gets the same permissions with zero setup - nobody has to remember which commands are safe, and nobody has their own private version of the answer. That is the difference between a personal setup and a team toolkit.
Isolation is a boundary. Instructions are a suggestion. A rule in CLAUDE.md is a preference the model can drift away from. A deny rule, a hook, or a checkout it cannot write to is not.

Two plans for the same feature: layered vs vertical slices

A vertical slice is one phase that cuts through every layer at once - schema, endpoint, UI, test - so it runs end to end on its own. A layered plan builds one floor at a time, which is why nothing works until the last phase, and every integration problem waits until then to show up.

Layered

Phase 1: Data layer
  - orders.schema.ts, migration 0007
  - OrderRepo.findById(id: string)
  - OrderRepo.create(dto: CreateOrderDto)

Phase 2: Service layer
  - OrderService with 6 methods

Phase 3: API layer
  - POST /orders  → createOrder()
  - GET  /orders/:id → getOrder()
  - error middleware in
    src/api/middleware/errors.ts

Phase 4: UI
Phase 5: Tests

Nothing runs end to end until phase 4. Exact paths and signatures for phase 3, which phase 1 will change. No link back to any user story - nothing says what it's for.

Vertical slices

Durable decisions
  - orders own their own line items
  - money is integer minor units
  - one write endpoint, idempotency key

Phase 1 (tracer bullet)
  One hardcoded order renders on the
  order page, through a real DB read,
  a real endpoint and a real test.
  Serves story: "see my order".

Phase 2
  Real order from the DB. Same route.

Phase 3
  Create an order. Same shape.

Out of scope: refunds, multi-currency.

Every phase runs, so every phase can be tested and demoed. Prose, not pseudocode. Durable decisions in a header; nothing brittle in later phases.

Reviewing these two plans took you a minute. Reviewing the two diffs they produce would take way longer. And the tell you can use this afternoon: a plan that comes back instantly, with no questions asked, is a bad plan. Every ambiguity in it got resolved by guessing. If it didn't ask you anything, ask it what it assumed.

How to go from an idea to shipped code

  1. capture the idea
  2. capture decisions
  3. write a spec
  4. write a plan with thin vertical slices
  5. tag each slice: watched, or safe unattended
  6. implement slice by slice
  7. review each

The spec, or PRD

What to build and what done means, in prose. The behaviour, the decisions that outlive implementation - data model, interfaces, dependencies - and an explicit Out of scope. The destination.

The plan

How to get there. The same feature cut into thin vertical slices, each small enough to finish in one session, each tagged watched or safe unattended, each pointing back at the spec. The journey.

Why an agent needs both: spec without plan, it takes one enormous swing at the whole thing. Plan without spec, it builds the wrong thing efficiently. Together they give it a fixed target and a session-sized next step, so no phase depends on it remembering the conversation.

The four rules that do the work

Vertical slices. Each one cuts through every layer and runs on its own, so it can be demoed and tested. A layered plan works nothing end to end until the last slice.

TDD in every slice. Tests first, then code until they pass. This is also what buys you the review shift later - no real tests, no reviewing the interface instead of the diff.

Name the docs it makes stale. Attached to the slice that breaks them, so they ship with the code instead of never.

A checkpoint before it writes. Reviewing a list costs seconds. Reviewing the finished plan costs you the session.

Then, running it: feed each slice three things - the spec, the whole plan, and which slice to build. Seeing what the later ones are for is how the agent knows what not to build now. Skip this and they duplicate and contradict each other.

This is the last step that deserves your full attention. After this the agent implements the plan and you review the result - so anything you didn't decide here, it decides for you.

Review the interface and the tests, not the function bodies

The interface
the names, the shape, what it promises to callers
you
The implementation
function bodies
the agent
The tests
what counts as proof it actually works
you

You become the interface designer. The agent becomes the implementation specialist.

The shift is what you review, not how fast. You stop reviewing implementation and start reviewing architecture: the boundary, the contract, and the evidence it holds. Not opaque - you can open any function any time, and sometimes you will. But by default your attention goes to the edges of the module, not its interior.

Pythonthe module's public functions, their type hints, and the test file
Reactthe component's props and the store's actions, plus what the tests assert

Same move in any stack: the surface other code depends on, plus the tests that pin it down.

This only holds where the tests are real. Weak feedback loop and it collapses - slow builds, hardware in the loop, mocks that pass while the feature is broken. Then you go back to reading the diff.

.claude/commands/prepush.md - kept in the repo, so everyone runs the same review

---
description: Review the current diff before pushing
---

Run `pnpm test` and `pnpm lint`.  # your checks
If anything fails, stop. Report the failures
and nothing else.
Do not review red code.

If the tests pass:
1. Run `git diff main...HEAD` and read the
   whole diff.
2. Judge it against exactly one acceptance
   criterion: $ARGUMENTS
3. List anything in the diff that does not
   serve that criterion.
4. Check it against docs/standards.md. Cite
   rules only from files you have read in
   this session - if you did not read one,
   say "no rules file read". Never cite a
   rule from memory.

Output: PASS, or the numbered list. Nothing else.

Four properties. Only the first is non-negotiable.

  • Refuses to review red code.Reviewing a diff whose tests fail is theatre. It is what makes this a gate rather than a summariser, and it is the line people leave out.
  • Checks against a stated criterion.Not “good practice”. One criterion, not five - a command asked to check five things checks none properly.
  • Cites rules only from files it read.Rules “from memory” are the most confident wrong output you'll get all day.
  • Runs every check you own, not just tests.Lint, typecheck, formatter, your coding standards. Write the standards down and point the command at the file - otherwise it guesses at them.

Why not the built-in one?

Claude Code ships /code-review (aliased /review) and /security-review. Build your own anyway: the shipped one doesn't know your acceptance criterion and won't refuse to run on red. Name it /prepush - a project command overrides a bundled skill of the same name, but not its aliases.

.claude/skills/implement-plan/SKILL.md

One more command, and this one runs the others. You give it the plan and the name of your review command. It takes the slices one at a time, and for each slice it starts an agent that writes the code, reviews its own work with your command, fixes what the review found, and reviews again - looping until the review comes back clean or it runs out of tries.
You are the orchestrator. Never write code yourself.
Args: the plan, and the review command to run.

Rules:
- First read CLAUDE.md, .claude/rules/ and any contract
  files. Condense them into one context block.
- Run the slices in order, one at a time. Wait for each.
- Start a fresh agent per slice. Give it the context
  block, the slice, and what earlier slices built.
- Each agent: implement, run the review, fix what it
  found, run the review again. Three cycles maximum.
- Then say "slice N complete", or stop and list what
  is still open.
- Never carry on past a slice that did not complete.

Why it is shaped like this

The orchestrator never writes code. It starts one agent per slice and reads the result, so its own window stays small enough to still be reliable at slice six.

Every slice agent starts on a fresh window. It inherits the codebase, not the transcript - the same trick as clearing between tasks, applied automatically.

Three cycles, not “until clean”. Then it stops and tells you. An unbounded fix loop is how you get a green suite and the wrong feature.

Conventions do not travel. A fresh agent knows nothing about your repo, so the rules get pasted into every single one.

It never carries on past a failure. A slice that cannot pass its own review stops the run instead of landing.

Help the agent find the bug instead of making it guess where to look

I expected the retry to stop after three attempts.
It kept going - the log shows attempt 9.

<paste the actual log lines here>

Show, don't describe

Paste the stack trace, the failing input, the screenshot, the log line. Your summary of an error is lossy; the error is not.

Then frame it

A pasted trace with no sentence around it makes the agent guess what “correct” looked like, so it debugs the error message instead of the problem. Two clauses fix that: what you expected, and what actually happened.

Works identically for a hardware trace, a serial dump, a failing assertion, a red CI job.

Past a few hundred lines, don't paste the log - point at it. Write it to a file and say which part matters, and it greps to that region instead of swallowing the file. A paste also dies with the session; the file survives a /clear.
